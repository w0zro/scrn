Guide.

Everything scrn does, in the order you'll meet it.

§ 1

Install

$ curl -fsSL https://raw.githubusercontent.com/w0zro/scrn/main/install.sh | sh

The script fetches the release built for this machine, verifies it against the release's checksums.txt, and puts the binary in ~/.local/bin with the manpage beside it — man scrn has all of this in reference order. scrn keeps its shells in tmux, so have that installed too (on a Mac: brew install tmux). Two variables override the script:

SCRN_INSTALL_DIRinstall somewhere else
SCRN_VERSIONa release other than the latest

Building from source works too, with Go 1.22 or later:

go install github.com/w0zro/scrn@latest
§ 2

First run

scrn

There is nothing else to set up beyond having tmux installed. The first shell brings up a tmux server of scrn's own — private socket, out of reach of any .tmux.conf — and every window attaches to it. By default scrn looks for repositories under ~/projects; point it elsewhere in the config.

The list opens showing what is running, so on a quiet machine it may say nothing running. Two keys from there:

.show every repository, running or not
/find one by name
§ 3

The navigator

The left column is a tree, at most four levels deep: group → repository → sub-project → process.

Repositories

Every git repository under your project roots. The scan skips node_modules, vendor, target, .build, Pods, .venv and venv, plus anything you add to skipDirs.

Groups

A folder inside a root that holds two or more repositories groups them. The group is a place of its own: s opens a shell at the folder, r runs the folder's plan, x covers everything beneath it.

Sub-projects

In a monorepo, a directory with a manifest is a project of its own and gets a row under its repository. Manifests, in the order they are trusted: .scrn, Procfile, package.json, deno.json, composer.json, go.mod, Cargo.toml, Gemfile, mix.exs, pyproject.toml, pom.xml, build.gradle. They are found through git ls-files — no tree walk, ignores respected, untracked files included.

Processes

Each place lists the processes running in it, attributed to the innermost place they belong to, and named by what you would call them — npm run dev, not node. Keys that shape the list:

spacefold or unfold the selected node; a folded node shows +n for what it hides
-fold or unfold everything; unfolded rows also show pids
.toggle between everything and only what's running

Dim rows are processes that were started outside scrn, on some other terminal. They are listed and killable, but there is no shell to step into.

/ finds processes as well as places: a query lists the ones whose command answers it, under the places they run, pruned to the branches that answer. enter steps into a found shell, and ctrl-x asks to kill what the cursor is on, without leaving the look. An empty query lists places alone.

§ 4

Shells

s opens a shell at the selected place. enter on a shell's row steps into it: keystrokes go to the shell. scrn keeps one key for itself: ctrl-space, the prefix — it reaches scrn from anywhere, even a focused shell, and every other keystroke belongs to the pane. The chords keep their letters' meanings: n steps back out to the navigator, j and k attach to the next and previous shell, another ctrl-space toggles back to the process you were in before, / opens the filter, s a A r open a shell, start an agent, continue a conversation, or run the plan where you are, v opens the reader, q quits, ? shows the keys. Anything unbound after it cancels it. The foot of the column wears the mode the keys are in, the way vim says INSERT: navigate at the list, proc inside a shell or its transcript, prefix while a chord hangs. The mode keeps the bottom line to itself; anything scrn has to say — a report, an error, a confirmation — appears above it.

cmd-v pastes even in a terminal that hands the chord to scrn instead of translating it: the clipboard is read, and the paste lands wherever typing goes — a focused shell, the filter, the picker.

Shells live in scrn's private tmux server, so they survive the window — close the terminal, quit the terminal app, come back and everything is where it was. The pane behaves the way a pane behaves in tmux, because it is one: keys, modes, mouse reporting, the alternate screen, all of it.

ctrl-space v opens the reader over what has scrolled away — the pager's screen included, so a line out of git log is three keys away. j k move, v marks and moving extends, y copies the marked lines to the system clipboard, esc puts down the mark and then the reading. Each shell keeps 10,000 lines of transcript by default — scrollback in the config raises it.

scrn mostly doesn't hold the mouse at all: dragging, double-clicking and copying are the terminal's own, everywhere, exactly as they are with no scrn in the middle. Only while the focused program has asked for the mouse — vim, htop — does scrn take it, and then every event crosses raw. The navigator never takes the mouse; the list is the keys' alone. A program that copies for itself — vim's clipboard yank, anything speaking OSC 52 — reaches the system clipboard just the same.

When several windows watch the same shell, it is sized for the smallest of them, so no window sees a torn screen.

§ 5

Agents

a starts an agent in the selected place, in a shell like any other — Claude Code, unless the config's agent names another kind. Kinds are unequal on purpose: each shows only what its tool actually advertises. Claude Code advertises everything — scrn reads the session files it leaves behind, so the navigator can show its state:

⠧turning — an instance is working
◆blocked mid-turn on something specific: a permission prompt, a question
●finished its turn, waiting for what you ask next
○idle since it started

The mark tells you, from across the list, which projects need attention — the ◆ most of all, since answering it resumes work already underway. The detail pane for a Claude row names what a blocked instance is waiting on and shows the tail of its transcript.

ctrl-space enter goes to the next agent waiting on you, from wherever the keys were going — a focused shell, the filter, the list. Pressing it again continues around the waiting ones in turn.

A conversation doesn't end when its instance exits; it's suspended, and the transcript is enough to pick it back up. A on a place lists what's suspended there — sub-projects included — newest first: when each conversation last moved, its branch, and the last thing you asked of it. Letters narrow the list the way the filter does, enter continues the one under the cursor in a shell opened where the conversation was had, and esc closes the list. A conversation an instance is still carrying isn't offered. Every kind that keeps conversations answers the picker, and each is continued by the kind that had it.

A kind that advertises nothing — an ollama REPL — is still an agent to start: its rows are plain processes, unmarked, which is the whole truth about them. Ollama runs the first model it lists, unless agentRuns names one.

§ 6

Plans

Working on a project usually means the same processes every time: the dev server, the test watcher, an agent. A project writes them down in .scrn — Procfile format, a name and a command per line:

.scrn
dev:   npm run dev
api:   go run ./cmd/api
agent: claude

Without one, scrn reads the conventions in this order: a Procfile means every line is a process; a package.json contributes only its dev or start script, whichever exists first.

r starts the plan's entries that aren't running, each in its own shell named for its entry. It is a list to run, not a supervisor: nothing restarts on its own, and a dead server shows as dead until you start it again.

§ 7

Killing

xkill the selected process
Xkill it and everything under it
x on a repo or groupkill everything running in it

Every kill asks first — x, y or enter confirms, anything else cancels. Processes get SIGTERM, and a signalled row wears a red marker until a rescan actually observes the exit; the list never claims an exit it hasn't seen. Kills work on any listed process, including ones scrn didn't start.

§ 8

Configuration

One JSON file, entirely optional. It lives at ~/.config/scrn/config.json (XDG_CONFIG_HOME is honored).

~/.config/scrn/config.json
{
  "projectsDirs": ["~/projects", "~/work/mono"],
  "scrollback": 50000,
  "navWidth": 34,
  "skipDirs": ["bazel-out", "dist"]
}
FIELDDEFAULT
projectsDir$HOME/projectsthe directory searched for repositories; ~ and $VARS expand
projectsDirs—several roots; when set, projectsDir is ignored. A root that only exists on another machine is fine
scrollback10000transcript lines each shell keeps. Settled into the server as the first shell brings it up, so raising it takes R — a fresh server — to reach anything
navWidth28the navigator column's width, 16–60
agentclaudethe kind of agent a starts: claude or ollama
agentRuns—what starting a kind runs, by name — {"ollama": "ollama run mistral"}
skipDirs—directory names the scan never enters, on top of the built-in list
§ 9

The server

The shells live in a tmux server of scrn's own: it owns the ptys, the emulation and the transcripts, and every window talks to it — one server per user, for all projects, on a socket at ~/.local/state/scrn/tmux-<uid>.sock (SCRN_SOCKET overrides, and XDG_STATE_HOME moves the directory) where no .tmux.conf reaches. Everything in a pane behaves the way it behaves in tmux, because it is tmux.

The server lives exactly as long as it holds something: the first shell brings it up, the last one closing takes it down. Upgrading scrn never disturbs it — the server is not scrn's binary, so a new build talks to the same server and the shells never notice. In a pinch the shells are reachable without scrn at all: tmux -S ~/.local/state/scrn/tmux-<uid>.sock attach.

scrn ls is the same state for scripts: the held shells, one per line on stdout — pid, directory and name, tab-separated. No server listening is an empty list, not an error.

§ 10

Upgrading

Install the new binary (the install script again, or go install). The shells live in the tmux server, not in scrn's binary, so an upgrade disturbs nothing: the next window simply talks to the same server. There is nothing to press, and nothing to notice.

§ 11

Linux

Linux builds are published for arm64 and amd64, cross-compiled and so far untested — reports welcome. scrn leans on two neighbors: tmux, whose server holds the shells, and lsof, which is how the process list is read:

apt install tmux lsof # or dnf, pacman, apk…
